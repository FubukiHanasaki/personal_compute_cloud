# Windows 与服务端逻辑检查

作者：FubukiHanasaki。日期：2026-11-03（Asia/Shanghai）。

按本轮要求，仅进行源码逻辑审查与静态检查。没有启动 Server、数据库、Agent、Windows Worker 或模型，没有执行 pytest、接口调用、部署演练或浏览器校验。以下结论不能替代 Windows 实机、Docker 生产部署或此前跳过的视觉验收。

## 审查范围

- Windows：独立运行时边界、AppContainer/SID 权限、句柄继承、原子 Job Object 归属、资源限制、启动/停止/输出清理、异常构造与 profile 恢复。
- Agent 与 Server 协议：领取去重、响应丢失、租约续期与过期、取消、停止确认、恢复日志和模型切换。
- Server：角色/作用域/资源授权、注册和凭证分离、事务与唯一约束、Shared 优先、服务状态与额度、输入/工件边界、备份恢复前置条件。

## 发现与修复

| 问题及触发条件 | 修复后的逻辑 |
|---|---|
| 取消后租约过期，sweep 将 cancel_requested 覆盖为 reconciling，后续可能重试 | 保留取消意图；attempt 仍进入 reconciling 并占用额度，确认停止后只进入 cancelled |
| Shared 节点将该服务设为 stopped，仍被当作优先可选节点，Private/Reserved 无法领取 | 当前节点与 Shared 优先候选共用服务停止排除条件 |
| 领取响应丢失后原 claim 已过期/已终结，pending claim 一直收到冲突 | 有待核对 attempt 时重放原身份；续租仍拒绝过期尝试，Agent 在启动前续租失败后报告停止。已确认结束的 claim 返回 204，不产生第二个 attempt |
| 模型切换时忽略旧后端停止失败，可能同时启动新后端 | 停止失败保留旧后端与 error 状态，并拒绝创建新后端 |
| 本地关闭某能力后，Server 不处理已有服务的 stopped 报告，造成额度卡住 | 已有服务继续接收状态报告；不具备能力时只下发 stopped，不要求预热 |
| Windows 创建失败且清理失败时，上层持有 worker=None，可能错误报告 stopped=true；探测也可能吞掉该异常 | 使用明确的未确认停止异常，保留日志并停止 Agent，等待人工核对；隔离探测同样向上传递该异常并中止启动 |
| Windows close 持有 stop 使用的锁并等待输出线程，输出超限线程可能反向等待该锁 | 使用独立清理锁，等待线程时不持有进程锁；未确认线程退出就拒绝继续释放资源 |
| Windows 部分管道创建失败可能泄漏先前句柄；清理重试可能重复 FreeSid；终止时存在进程退出竞态 | 每对管道创建即记录，逐个完成释放；成功释放的 SID/profile/ACE 立即清空标记；进程已自行退出时接受停止结果 |
| Worker 创建较慢或网络延迟时，启动和本地截止时间可能晚于租约；结果上传前续租未更新本地守卫 | 守卫在创建前启动；领取截止时间保守扣除请求耗时；Windows 挂起进程启动前检查租约，并先设置启动计时再恢复线程/写 stdin。构造成功后切换到任务墙钟计时，后续租约由独立守卫跟踪，不把初始租约固化为总运行时限；上传前续租同步更新守卫 |
| 未核对的 active-attempt 存在时，Agent 初始化仍会探测执行能力，主循环还会预热模型 | 初始化跳过探测，恢复命令跳过探测；未核对日志阻止模型预热和新领取 |
| 巨大整数、列表形式的 role/size、嵌套 NaN 可能触发 OverflowError/TypeError/ValueError，变成 500 | 在转换和集合查询前校验大小与类型；非法 JSON 数值统一返回 422 |
| Compose 恢复只依赖 pg_restore 表重名报错，含其他表的目标库仍可能被导入 | 与原生恢复共用空库/空工件目录前置检查，拒绝已有用户表、视图和序列；清单必须是普通文件 |
