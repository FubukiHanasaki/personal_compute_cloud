# 受管推理内存与升级

作者：FubukiHanasaki。

本版移除旧的受管推理物理内存额度判断。Ollama / ComfyUI / NInfer 统一采用独立预算与启动门槛；缺少新配置的受管节点心跳返回 422，不回退旧设置。纯 compute / synthetic 节点仍使用物理资源配置。

## 三种数值

| 字段                                            | 用途                                                                            |
| ----------------------------------------------- | ------------------------------------------------------------------------------- |
| 模型 `resources.memory_mb`                      | 单个受管进程树的硬上限；Windows 为 Job 提交内存限制，Linux 仍为 cgroup 内存限制 |
| Agent `managed_commit_budget_mb`                | 节点管理员的受管推理内存总预算，独立于物理容量；允许大于 `physical.memory_mb`   |
| Agent `managed_available_memory_mb[完整worker]` | 启动 / 调用该模型前必须满足的真实物理空闲 MiB                                   |

`physical`、`available` 和计算用的 `allocatable` 继续上报真实资源。进程硬上限不是已占用的物理内存，也不是提前向操作系统预留的提交空间。独立预算不创建分页文件、不保证系统剩余提交空间，也不保证满上下文下性能或内存安全；保留现有 CPU、显存、并发、策略、负载及进程隔离保护。

## Windows 配置片段

将下面字段合并到原 `agent.toml`，保留现有服务器地址、凭证、路径和所有模型设置。根字段必须置于任何 `[table]` 之前，或在已有根字段位置添加。

```toml
managed_commit_budget_mb = 32768

[managed_available_memory_mb]
"ollama:pcc-qwen3.5-9b:q5_k_m" = 4096
"ollama:pcc-qwen3-vl-8b:q5_k_m" = 4096
"comfyui:sdxl-lightning-4step" = 10240
"comfyui:qwen-image-2.1" = 13312
"ninfer:qwen3.8-27b-nvfp4" = 5120
"ninfer:qwen3.8-27b-nvfp4-256k" = 5120
```

这些门槛来自用户提供的 58 次试验结论，本项目未重复执行该压力试验，不能外推到其他节点或满上下文负载。worker 必须与本机实际启用的完整 ID 一致；如还有其他受管模型，必须为其补充经过本机验证的门槛。表允许最多 32 项，值为严格整数 1024–1048576 MiB。预算为严格整数，有受管模型或门槛表时至少 1024 MiB，最多 1048576 MiB；仅非推理节点可保留 0。

预算 32768 MiB 适用于当前单任务串行额度，可容纳单个 32768 MiB 模型。不要据此提高并发。六个模型原提交额度保持 16384、16384、20480、32768、30720、32768 MiB，不修改上下文、KV、视觉、思考、授权或 API Key。现有 `nvfp4` / `k8v4` KV 值继续接受，不能静默替换为 fp8。

Agent GUI“资源与共享”提供预算和逐行门槛输入；服务端节点详情分别显示物理内存、推理预算和门槛。物理内存圆环只表示物理负载，不表示提交预算占用率。

## 调度、预热与占用

受管任务检查预算减去已计账进程额度是否覆盖模型硬上限，并检查实际空闲 RAM 是否达到该完整 worker 门槛。空闲服务的声明额度不能加到物理可用 RAM 上。compute / synthetic 仍采用原有物理资源判断。

活动 / 待核对任务和启动中、停止中、错误待核对服务继续占用资源；已有任务对应的服务不重复计账。空闲模型仅在确认旧进程停止后才切换复用资源。Agent 本地调用和预热使用同一资源判定；暂不对已加载模型降低门槛。物理空闲不足时，预热保持停止 / 等待，不创建假占用；必须等待新心跳和资源条件改善。

排队原因与实际任务准入共用判断，包括提交预算不足、物理空闲低于门槛、CPU / 显存不足、并发、维护模式、离线和负载保护。检查通过后显示等待符合条件的节点领取；条件仍以实际领取时的事务快照为准。

## 升级顺序（由部署者执行）

1. 将节点置于维护模式，停止接新任务；完成或确认停止已有任务。停止 Windows Agent 的自动运行及模型预热。
2. 在服务器确认实际运行目录、PM2_HOME、进程名、Git 分支与提交、工作区改动和本地补丁。历史为 `/root/personal_compute_cloud`、`PM2_HOME=/root/personal_compute_cloud/tmp/pm2`、`pcc-server`，必须以现场为准。先备份源码变更、数据库、工件和配置；生产备份必须与现有部署方式匹配，不能直接套用 Compose 脚本。
3. 保留现场 `nvfp4/k8v4` 修改的补丁及语义。新版已接受这两种 KV，但仍需核对现场是否有其他改动；有本地源码改动时，自动更新脚本会拒绝，先人工审查合并，不执行 reset/clean 或盲目丢弃补丁。
4. 停止现有后端，更新后端及前端、安装依赖和构建。没有新增数据库结构，不需要新迁移，不重置数据库，不更换密钥，不改 Caddy / TLS。
5. 启动原服务，核对运行 SHA、PM2 稳定状态及真实配置的 `/healthz`。本地历史监听为 `127.0.0.1:8000`，应以现场为准。
6. 更新 Windows Agent，合并预算与全部 worker 门槛；确保另一 Agent 的本地适配与该协议一致。使用新配置启动到维护模式，确认心跳 200、能力中预算及门槛正确、物理数据未伪造，再恢复共享 / 预留等原模式。
7. 检查模型原额度及参数，先提交小任务，验证领取硬上限不变、低于门槛时排队原因正确，再逐步恢复实际模型负载。

历史受管 Agent 的缺字段心跳本版明确拒绝；不再提供旧配置兼容。升级不能只启用门槛字段，必须同时部署提交预算和本地准入。若回退，需将后端、Agent 版本及配置一起恢复，保留注册凭证和模型配置；禁止仅回退代码后删除新字段并恢复接单而不核对安全状态。

本次用户选择自行部署；开发环境不会操作生产机器。生产健康状态须由部署完成后的实际检查确认。
